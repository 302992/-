# MuJoCo Playground：环境与配置结构说明

这份文档帮你回答三个问题：**这套软件由什么组成，训练时数据怎样流动，想改变行为应该改哪个文件。** 它是查阅手册，不要求按顺序复制命令。

真正开始动手时，请打开另一份 [四足速度跟踪手把手教程](四足速度跟踪手把手教程.md)。教程围绕一个独立的宇树四足实验展开；读到不理解的概念，再回来查对应部分。

本文按本仓库当前源码编写。文中的 Go1 维度、参数和 CLI 行为指仓库自带实现；教程中的 Go2 适配、配置和训练入口以教学项目为准，不能默认与官方内置任务完全相同。

## 1. 先分清四样东西

假设你想让机械狗收到“前进 0.5 米/秒”的指令后向前走。至少需要以下四部分：

| 部分 | 它回答什么问题 | 例子 |
| --- | --- | --- |
| **机器人模型** | 这只狗的身体、关节和电机是什么样的？ | Go2 的 XML、网格、质量、关节限制 |
| **任务环境** | 给控制者看什么、怎样控制、怎样算做得好？ | 观测包含速度指令；奖励鼓励跟踪目标速度 |
| **学习算法** | 根据尝试的结果，怎样调整控制者？ | PPO 更新神经网络参数 |
| **策略** | 此刻看到这些信息，下一步该怎样动？ | 训练后的网络输出 12 个关节控制量 |

下载一个 Go2 模型，解决的是第一项。它不会自带“前进、后退、转弯”的技能；还要接上任务环境和算法训练策略。检查点也不是新的机器人模型，它是训练过程中保存下来的网络数据。

## 2. MuJoCo、Playground、MJX、JAX、Brax 的关系

可以按下面这条链理解：

```text
你提出目标：让机械狗跟踪速度指令
        │
        ▼
Playground 任务环境
  定义初始状态、观测、动作、奖励、结束条件
        │                           ▲
        │ 把动作送去仿真             │ 收回新的物理状态
        ▼                           │
MuJoCo / MJX：推进物理世界 ───────────┘

环境交互产生的经验 → Brax 中的 PPO → 更新策略网络
                         │
                         └─ 使用 JAX 进行数组计算、自动微分和编译
```

- **MuJoCo** 是物理引擎，负责算受力、运动、碰撞和关节约束。单独使用 MuJoCo，也可以写控制程序和强化学习任务。
- **MJX** 提供可加速、可批量执行的 MuJoCo 仿真能力。本仓库区分 `jax` 和 `warp` 实现；选择一种后端，并不改变“观察—动作—反馈”的学习概念。
- **MuJoCo Playground** 提供许多已经定义好的任务，以及连接训练、批量仿真和渲染的工具。它让你少写一些基础工作，但任务设计仍需要自己理解。
- **JAX** 是计算工具。这里的物理仿真和学习会用到它的数组、编译、自动微分和并行能力。
- **Brax** 是另一套项目；本文用到的是其中的 PPO 实现。不能把“用 Brax 训练”理解成不再使用 MuJoCo 物理模型。
- **PPO** 是一种强化学习算法。它反复收集经验、计算哪些行为值得加强，再更新策略。

仓库还提供 RSL-RL 的训练入口。初学时沿着一条训练路线走通即可，不必一开始同时掌握所有后端和算法库。

## 3. 速度指令到底位于哪一层？

四足速度跟踪常把上层指令写成三个数：

```text
command = [vx, vy, wz]
```

| 分量 | 含义 | 常见单位与符号 |
| --- | --- | --- |
| `vx` | 沿机身前方的目标线速度 | 米/秒；正值前进，负值后退 |
| `vy` | 沿机身左侧的目标线速度 | 米/秒；正值向左平移 |
| `wz` | 绕竖直轴的目标转动速度 | 弧度/秒；正值左转，负值右转 |

**左转和左平移不是同一个目标。** 教程中的前进、后退、左转、右转主要使用 `vx` 和 `wz`；`vy` 可以先固定为 0。

机身坐标系也不同于世界坐标系：狗转身后，“向前”跟着它的朝向改变，而不是永远朝地面的某个固定方向。

```text
上层速度指令 [vx, vy, wz]
        │ 作为观测的一部分
        ▼
策略读取：速度、姿态、关节状态、上一动作、目标指令
        │
        ▼
输出 12 维 action
        │ 缩放并叠加到默认关节姿态
        ▼
关节目标位置 → 位置控制器产生力矩 → 狗发生运动
        │
        ▼
环境比较“实际速度”和“目标速度”，计算跟踪奖励
```

因此，`action` 一般不是“前进/后退/左转/右转”四个按钮。策略需要学习如何让 12 个关节配合运动，才能实现一个速度目标。换一个指令时，通常不需要换四个不同的网络，而是让同一个策略根据不同指令作出反应。

仓库自带的 Go1 摇杆任务会在训练中采样速度指令。“Joystick”是任务命名，不表示训练时必须接一个真实手柄。评估时固定或切换指令，才能清楚检验前进、后退和转向能力。

## 4. 环境返回的数据是什么？

### 4.1 Playground 的接口

```python
state = env.reset(rng)
state = env.step(state, action)
```

`reset` 产生一个回合的初始状态。`step` 根据旧状态和动作，返回新的状态；调用者必须接住返回值。

这不是 Gymnasium 的五元组接口。如果某个算法库要求 `obs, reward, terminated, truncated, info`，还需要适配层，不能只把参数名改一下。

### 4.2 `State` 容器的六部分

| 字段 | 内容 | 学习时怎样理解 |
| --- | --- | --- |
| `state.data` | 位置、速度、接触等物理仿真数据 | 仿真里的完整世界信息 |
| `state.obs` | 策略或价值网络的输入 | 控制者被允许看到的信息 |
| `state.reward` | 本次环境步的奖励 | 做完这个动作后的分数 |
| `state.done` | 环境的结束标志 | 本次尝试是否应结束 |
| `state.metrics` | 奖励分量、诊断数值等 | 帮人判断学习过程 |
| `state.info` | 任务内部需要延续的数据 | 上一动作、当前指令、随机 key、计时器等 |

**`state` 不等于 `state.obs`。** 完整仿真状态可以包含训练时使用、部署时拿不到的信息；策略真正读取的是指定的观测。

### 4.3 Actor 和 Critic 看什么？

PPO 通常有两个网络：Actor 决定动作，Critic 估计未来能拿到多少奖励，帮助优化 Actor。部分机器人任务让两者看不同信息：

- `state`：供策略使用的普通观测。
- `privileged_state`：额外包含真实速度、接触、力矩等仿真信息，供价值网络训练使用。

本仓库原始 Go1 摇杆任务在当前配置下，普通观测为 **48 维**，特权观测为 **123 维**，动作为 **12 维**。48 维普通观测包括线速度 3、角速度 3、重力方向 3、关节位置偏差 12、关节速度 12、上一动作 12、速度指令 3。

这些数字由任务的观测构造代码决定，不是所有机器人固定相同。改了观测结构，旧检查点往往就不能直接使用。

### 4.4 回合终止、超时、自动重置

环境自身可以判断失败，例如身体翻转。训练还需要一个最大回合时长，防止某次尝试无限持续。

[`wrapper.py`](../mujoco_playground/_src/wrapper.py) 的训练包装器负责连接批量环境、最大回合长度和自动重置。直接调用原始 `env.step`，不代表已经拥有全部训练行为。仓库原始 Go1 的失败条件与教程适配任务可能不同，应阅读各自的终止代码。

## 5. 两类配置：先问“我是在改任务，还是改学习方法？”

### 5.1 环境配置：改变狗所处的任务

环境类附近的 `default_config()` 定义这类参数。例如原始 Go1 的配置位于 [`go1/joystick.py`](../mujoco_playground/_src/locomotion/go1/joystick.py)。

| 例子 | 含义 | 改动影响 |
| --- | --- | --- |
| `command_config` | 目标速度怎样采样 | 狗需要适应哪些指令 |
| `reward_config.scales` | 不同奖励项的权重 | 更重视跟踪速度、稳定姿态还是节省动作 |
| `noise_config` | 观测噪声 | 策略能看到多准确的信息 |
| `action_scale` | 网络输出缩放多少 | 同样一个动作对关节目标影响多大 |
| `Kp`、`Kd` | 关节位置控制相关增益 | 关节跟踪目标时的响应 |
| `ctrl_dt`、`sim_dt` | 控制与物理仿真时间间隔 | 动作更新频率与仿真推进频率 |
| `impl` | 使用哪种 MJX 实现 | 仿真后端及所需依赖 |

原始 Go1 中 `ctrl_dt=0.02`、`sim_dt=0.004`，即一个控制步内部执行 5 个物理小步。算法侧的 `action_repeat` 还可以重复一个动作，不能把它与仿真小步混为一谈。

### 5.2 PPO 配置：改变怎样学习

这类参数主要在 [`mujoco_playground/config/`](../mujoco_playground/config/) 或自己的训练入口中。

| 参数 | 最初需要理解的意思 |
| --- | --- |
| `num_timesteps` | 所有并行环境合计的采样预算 |
| `num_envs` | 同时运行多少个训练环境 |
| `episode_length` | 训练包装器限制的回合长度 |
| `learning_rate` | 每次更新网络的步长 |
| `unroll_length` | 每段采样序列有多少步 |
| `batch_size`、`num_minibatches` | 经验怎样组成优化批次 |
| `num_updates_per_batch` | 同一批经验重复优化几轮 |
| `network_factory` | Actor/Critic 结构及使用哪些观测键 |
| `num_evals`、`num_eval_envs` | 评估次数和评估并行数 |

调小 `num_envs` 主要改变训练资源与吞吐量；改变速度奖励权重，则改变任务偏好。这两种改动应该分别记录，避免不知道实验结果为何改变。

当前 Brax PPO 有约束：`batch_size × num_minibatches` 必须能被 `num_envs` 整除。多设备训练还要求并行环境数与设备数匹配。不能把每个参数都当成彼此独立的开关。

### 5.3 参数最后是怎样生效的？

**对仓库自带 `train-jax-ppo`：**

```text
任务类的 default_config()
        └─ CLI 构造环境覆盖项 → registry.load → 环境构造函数应用覆盖

config/*_params.py 的任务 PPO 配置
        └─ 显式传入的 CLI 参数覆盖 → 传给 Brax PPO
```

几个容易混淆的地方：

- CLI 代码中 `flags.DEFINE_*` 的默认数字，不一定是实际训练默认值。只有明确传入的部分参数才覆盖任务 PPO 配置。
- 原始 Go1 摇杆任务的 PPO 配置是 2 亿步、8192 个并行环境；不要把脚本里通用 flag 的默认值当成这项任务的默认值。
- 在自己写的 Python 程序中修改 `config`，不会改变另一个终端里 CLI 创建的环境。必须让本次训练实际接收这份配置。
- 环境和 PPO 两处可能都出现 `episode_length` 等名称。要看训练入口把哪个值传给包装器，不能仅凭名字推断。
- JSON 环境覆盖使用带点的键名，例如 `reward_config.scales.tracking_lin_vel`；不是每个环境都存在相同字段。

最可靠的依据是**本次运行最终打印、保存的配置**。教程使用独立入口时，请以教程项目自己的配置合并规则为准，不要混用官方 CLI 的规则。

## 7. 本机 `mujoco_models` 可以怎样利用？

本机已经有：

```text
~/mujoco_models/mujoco_menagerie/
├── unitree_go1/
└── unitree_go2/
    ├── go2.xml
    ├── go2_mjx.xml
    ├── scene.xml
    ├── scene_mjx.xml
    └── assets/…
```

**可以复用这些模型文件。** Playground 也已经通过软链接使用同一份 Menagerie，无需把整个模型库再复制进项目。

但“用 Go2 模型替换 Go1 文件路径”通常还不够：

1. **物理描述不同**：质量、尺寸、关节限制、默认姿态和执行器设置可能不同。
2. **名称和顺序不同**：身体、脚部 site、传感器和关节顺序必须与任务代码对应，不能只确认两者都有 12 个电机。
3. **训练所需信息不同**：模型能打开，不表示已经提供环境奖励用到的接触与速度传感器。
4. **控制参数需要核对**：位置目标、控制增益、缩放和限幅必须匹配模型。
5. **策略不能凭维度相同通用**：Go1 的 12 维策略不因此自动适用于 Go2。

Go2 本机同时提供普通版和 MJX 版模型。配合 MJX 学习时优先核对 `go2_mjx.xml` 及其场景；模型 README 中关于旧版 MJX 限制的描述需要结合当前实际版本看，不能当作今天所有几何支持范围的完整说明。

教程中的 Go2 接入是一个本地教学适配任务，不等于上游已经内置了同名 Go2 环境。它复用本机资产，在项目内增加适配逻辑；模型源文件本身无需为了学习实验而被覆盖。

## 8. 新任务怎样接入训练？

有两条路线，理解它们的区别即可。

### 8.1 独立训练入口：适合开始学习

自己的程序创建环境对象，再把对象传给 PPO。这样不需要先给全局 registry 注册名字，也不必修改官方训练脚本。教学项目采用独立入口，便于看清自己的文件和上游文件的边界。

这条路线中，自己的程序需要负责配置、日志、保存检查点和评估。官方训练脚本已经实现的功能，不会因为导入了 Playground 就自动出现。

### 8.2 按名称接入官方 CLI：适合后续整理

若要运行 `train-jax-ppo --env_name MyTask`，还需要：

- 在对应任务组注册环境类和配置工厂。
- 让官方训练脚本的 `get_rl_config()` 能选到这个任务的算法配置；部分配置函数还会检查任务名。
- 保证注册代码在训练进程中被执行。另开 Python 注册一次后退出，不会永久影响后续进程。

根 `registry.ALL_ENVS` 是导入时组合的任务名元组。动态注册后，它不一定自动反映新任务；加载查找与打印的静态列表要分别理解。

**资产路径、环境注册和 PPO 参数是三件事。** 修改 Menagerie 路径不会自动完成任务注册；注册名称也不会自动产生合适的 PPO 参数。

## 9. 一次实验会留下什么？

常见产物有：

| 产物 | 用处 | 容易误解的地方 |
| --- | --- | --- |
| 环境配置快照 | 知道当时用了什么任务参数 | 不必然包含完整 PPO 配置 |
| 数字检查点目录 | 保存 Actor、Critic、观测归一化统计等 | 不是机器人 XML，也不是一段视频 |
| `ppo_network_config.json` | 帮助重建网络 | 不能替代环境和模型适配 |
| TensorBoard event 文件 | 保存奖励等标量曲线 | 只启动 TensorBoard 不会自动产生日志 |
| MP4 | 观察某次评估的动作 | 有视频不等于已稳定完成任务 |
| 命令与代码版本记录 | 解释为什么两个实验不同 | 应和训练预算、种子一起保留 |

当前官方 JAX 入口把环境配置写在 `checkpoints/config.json`，网络配置放在数字检查点内，没有单独保存完整 PPO 运行配置。自己的项目应主动保存最终配置与运行参数。

当前 Brax PPO 的这些检查点可用于加载参数继续学习，但没有保存并恢复完整的 Adam 优化器状态和原始训练步数，因此不能把它称作完整训练状态的无缝续跑。原始计数和新实验计数也不能直接相加理解为日志自动连续。

评估时要保持模型、观测维度、观测键、网络结构和动作处理一致。速度目标应当既传给任务内部计算奖励，也进入策略观测；只改屏幕上的文字，不能改变狗实际收到的指令。

## 10. JAX 写法为什么与普通 Python 不太一样？

JAX 把环境与网络编译后反复执行。第一次运行可能等待编译，后续执行才快；增加并行数、改变形状等操作可能触发重新编译。

最初只需记住以下规则：

- 随机数使用显式 key，并通过 `jax.random.split` 分给不同用途。反复使用同一个 key 会得到相同随机结果。
- 数组更新常写成 `x = x.at[i].set(value)`；状态更新常使用 `state.replace(...)`。
- JIT 内不能随意用依赖数组数值的 Python `if`；通常用 `jax.numpy.where` 或 JAX 控制流。
- `reset` 和 `step` 返回的数组形状、观测字典、`metrics` / `info` 的结构应保持一致。
- `float(...)`、打印和 Python 循环适合初学调试；在大量并行训练中频繁把设备数据取回会影响速度。

`jit` 表示编译函数；`vmap` 表示把同一函数应用到一批输入；`scan` 表示适合编译的循环。先理解一个环境走一步，再阅读并行与训练包装器，会更容易。

## 11. 本机安装记录与常见问题

### 11.1 先把“已验证的历史”和“当前运行”分清

2026-10-22 的检查曾确认：Python 3.12.15、Playground 0.2.0、JAX / jaxlib 0.6.2、MuJoCo / mujoco-mjx 3.6.0、Brax 0.14.2；GPU 为 RTX 4060 系列笔记本显卡，约 8GB 显存。Cartpole 的 GPU 短训练、TensorBoard 日志、检查点和 MP4 都已生成。

历史检查目录是 `logs/installation_check/CartpoleBalance-20261022-102813-install-check/`。它说明当时安装与训练链路可用，不证明此后所有任务、所有默认并行数都已经训练成功。今天的四足验证范围和结果以手把手教程中的记录为准。

### 11.2 按现象定位问题

| 现象 | 先检查什么 |
| --- | --- |
| JAX 使用 CPU 或初始化 CUDA 失败 | 解释器是否为 `.venv`；驱动及当前沙箱/容器的显卡访问权限 |
| Python 直接加载时要求 Warp | 某些任务默认 `impl="warp"`；本机入门路线明确选择 `jax` |
| 模型或网格找不到 | Menagerie 路径、软链接目标、对应模型的资产目录与版本 |
| 显存不足 | 并行训练/评估数、批次、序列长度及其他 GPU 进程；同步核对整除约束 |
| 奖励不上升 | 指令是否真的进入观测、奖励符号、动作控制、终止条件、训练量与视频行为 |
| 打印训练结束后才报 EGL / ffmpeg 错误 | 区分参数学习和后续渲染，先查看检查点是否已保存 |
| TensorBoard 没有曲线 | 训练是否启用日志、event 文件是否存在、服务是否指向正确实验目录 |
| 包在依赖同步后发生变化 | 检查 `pyproject.toml`、`uv.lock` 和实际选择的 extras / groups |

8GB 显存能否容纳某套参数需要实测。减少并行数可以帮助入门，但不能因此承诺某个训练预算必然收敛。GPU 速度快，也不能修正设计错误的奖励。

维护已有环境时无需先整体升级依赖。`uv.lock` 用于锁定版本；CUDA 属于本项目的可选依赖组之一。若主动重建环境，先弄清同步命令选择了哪些 extras；不要为运行一段示例而无意改变整个训练栈。

### 11.3 当前官方入口的几个已知细节

这些细节指原仓库的 `learning/train_jax_ppo.py`，不能直接套到教学入口：

- 使用 `--use_tb` 才会写 TensorBoard 日志，且需要 `tensorboardX`。
- 其 `--load_checkpoint_path` 对目录会继续搜索数字子目录，因此应传检查点父目录。
- 正常训练时省略 `--play_only`；当前脚本会把 `--play_only=False` 的“出现”也作为零步训练处理。
- rscope 的轨迹导出调用在当前脚本中被注释，安装包不代表实时轨迹流程已经启用。
- 本机 Brax 的 `checkpoint.load_policy` 对部分含空初始化器的配置有读取问题；教程使用经核验的加载路径。

这些内容在升级后可能改变。遇到类似问题，先核对你运行的入口和本机源码，再按错误信息定位。

## 12. 后续阅读顺序

第一次学习请以 [手把手教程](四足速度跟踪手把手教程.md) 的实际操作为主。开始阅读源码后，可按这个顺序：

1. 指令在哪里定义、采样、写入观测？
2. 策略的动作经过什么缩放，怎样作用到关节？
3. 实际速度从哪里读取，跟踪奖励怎样计算？
4. 回合怎样重置，失败与超时怎样处理？
5. 这些环境对象怎样交给 PPO，配置怎样保存？
6. 最后再阅读 PPO 的优势估计、损失函数和优化循环。

本机还有 [运动控制 Notebook](../learning/notebooks/locomotion.ipynb) 与 [经典控制 Notebook](../learning/notebooks/dm_control_suite.ipynb)。它们适合补充交互实验；其中面向云端的安装单元格，应先看懂作用再决定是否执行。
